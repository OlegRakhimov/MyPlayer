# FreeLocalPlayer — этап 0-B.3: ручное восстановление UUID уже просканированного файла

## Что было проверено в исходниках

- 0-B.1 уже хранит удалённые пользователем записи с UUID и текстом в `retiredMedia` и позиции `playlistPlaces`, а 0-B.2 добавил консервативный механизм повторного связывания **ещё не добавленного** MediaStore-кандидата.
- Но `DeviceMediaScanner.scan` автоматически добавляет новые файлы в `LibraryState.media`. Поэтому после реиндексации в обычной ситуации новый URI уже существует как отдельная живая запись с временным UUID, а прежний UUID находится в `retiredMedia`.
- `MusicDataRepository` хранит MIDI, аккорды, автоматические оценки и правки под SHA-256 UUID; смещения хранятся под таким же ключом в preferences. `player_shortcuts_v1` содержит историю и избранное; `playback_resume_v1` — сохранённую контрольную точку Media3.

## Добавленная функция

- `ConfirmedRetiredMediaRebind.preview(state, oldUuid, candidateUuid)` проверяет наличие старой удалённой записи и новой живой записи, соответствие типа/положительных размера и длительности, отсутствие пользовательского текста и упоминаний новой записи в плейлистах, уникальность URI/sourceKey и строгую согласованность sourceKey с MediaStore URI. **Это не алгоритм распознавания содержимого песни.**
- `ConfirmedRetiredMediaRebind.confirmed(..., userConfirmed=true)` повторно выполняет проверки и в копии `LibraryState` заменяет живую временную запись восстановленной старой, оставляя прежний UUID и оригинальный текст. Позиции `playlistPlaces` возвращаются в существующие плейлисты, другая архивная информация не изменяется.
- `MusicDataRepository.hasStoredDataForUuid` проверяет наличие файлов `.mid`, `.chords`, `.auto.chords`, `.chord-edits` и смещения у временного UUID, чтобы не удалить связь с собственными данными нового файла.
- `MainActivity` отказывает, если временный UUID присутствует в избранном, недавних, очереди Media3 или отдельной контрольной точке возобновления; если занято сохранение/сканирование/анализ; если выбранный URI недоступен или текущие MediaStore NAME, SIZE, DURATION/длина открытого файла отличаются от сохранённых данных.
- Интерфейс: **резервная копия** в главном заголовке → **Восстановить связь удалённого трека**. Пользователь выбирает старую запись и новый уже просканированный файл, видит обе метаданные, подтверждает вручную, затем выполняет SAF ZIP экспорт через существующий `AppDataBackup.exportTo`. Подтверждение доступно только после успешного экспорта **этого же снимка** медиатеки, и повторной проверки без конфликта. ZIP не импортируется автоматически.
- `LibraryStore.saveConfirmed` фиксирует новое состояние. UI сообщает об успехе только после подтверждённого `SharedPreferences.commit()`, не удаляет старые MIDI/аккордовые файлы. Изменение `applicationId`, переход на Room-primary, `pm clear` и переустановка APK не требуются для подготовки к проверке.

## Ограничения и строгие ворота

1. **Временный UUID должен быть полностью свободен от собственных пользовательских привязок**, иначе операция блокируется. Не реализовано слияние двух наборов MIDI/текстов/избранного. Оно требует отдельного безопасного UI и тестов, без удаления/перезаписи файлов.
2. **Старая запись должна уже быть в `retiredMedia`**. Если файл просто перемещён вне приложения, а старая запись осталась `live`, этот этап не выполняет автоматическое восстановление; понадобится отдельная процедура диагностики «недоступных живых записей».
3. **Положительные известные значения размера и длительности обязательны.** Старые записанные без метаданных объекты пока не поддерживаются. Даже точные совпадения этих чисел не доказывают тождество музыки: нужен осознанный выбор пользователя.
4. UI не подменяет исторические UUID в sidecar-файлах и не меняет исходные медиафайлы. При конфликте `saveConfirmed` запись не подтверждается, пользователь должен сохранить резервную копию и проверить исходное состояние.
5. Ручной UI и реальная доступность MediaStore должны быть отдельно проверены на физической Motorola после Gradle PASS. **Не запускать проверку, удаляя реальные песни или очищая данные телефона.** Сначала на отдельной тестовой библиотеке и с проверенным SAF ZIP.
6. Запуск Windows QA **только компилирует** app и исполняет JVM-тесты, ничего не устанавливая на телефон. Рабочий APK версии 1.3.12 (20) останется прежним, пока не будет утверждён следующий шаг.
