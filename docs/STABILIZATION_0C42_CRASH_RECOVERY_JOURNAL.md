# FreeLocalPlayer — 0-C.4.2: восстановление прерванной записи медиатеки

## Что было не защищено

Последовательность `submit() → фоновые JSON-сериализация и SharedPreferences.commit()` могла прерваться при остановке процесса до сохранения основной библиотеки. Этапы 0-C.4 и 0-C.4.1 устранили **ложное подтверждение**, но сами по себе не восстанавливали незавершённые записи.

## Механизм

Новый `LibraryPendingWriteJournal` создаёт приложение-приватный, версионированный файл `files/flp-pending-library-0c42.json` с SHA-256 **предыдущего** и **желаемого** JSON и полной копией последнего. Используется `android.util.AtomicFile` (атомарная запись с синхронизацией файла).

1. Фоновый одиночный writer сначала проверяет структуру ожидаемого `LibraryState`, сериализует JSON и **синхронно сохраняет журнал**.
2. Затем выполняет прежний `SharedPreferences.commit()`, который остаётся **единственным каноническим источником**.
3. Если `commit()` завершился успешно, журнал удаляется. Room обновляется как необязательная теневая копия.
4. После холодного запуска сначала проверяется существующий канонический JSON. При наличии журнала:
   - если текущий JSON равен **желаемому** по SHA-256 — предыдущий commit уже завершился, журнал очищается без повторной записи;
   - если текущий JSON равен **исходному** по SHA-256 — желаемый JSON проверяется строгим decoder и затем подтверждённо записывается;
   - если хеш отличается от обоих либо журнал повреждён — **запись не выполняется, журнал сохраняется, загрузка fail-closed**. Никакого автоматического удаления/отката свежей медиатеки.
5. Импорт SAF ZIP и действия по обновлению не меняют формат. Существующий барьер writer при экспорте/импорте сохраняется.

## Честные границы

Это **не полная гарантия сохранения после внезапного отключения питания**. Уязвимое окно остаётся **до успешного сохранения журнала** (включая время ожидания записи в очереди). При резком выключении питания файловая система и накопитель могут потерять уже синхронизированные блоки. При конфликте журнал намеренно не перезаписывает свежий JSON; требуется разбор. Дополнительный fsync и полный JSON в журнале могут снизить скорость сохранения очень большой медиатеки, поэтому нужен замер на 5–20 тысяч треков до релиза.

## Безопасность

- Отдельное имя журнала внутри `filesDir`; без новой `applicationId`, разрешений или Room migration.
- `allowBackup=false` не меняется; экспортируемый ZIP формат не меняется; обычный ZIP по-прежнему не содержит этого временного журнала.
- Android instrumented-тесты работают **только** на Motorola, в случайных `__flp_0c42_*` каталогах и SharedPreferences. Никаких вызовов удаления/очистки/переименования основной медиатеки.
- Тесты: 6 JVM чистого решения + 6 Android на изолированном журнале и хранилище; реальные события `am force-stop` с незавершённой записью **не вызываются**.
- Перед обновлением телефона строгий SAF ZIP audit, подписи APK и SHA-256 реального JSON. После Android QA проверка исходного SHA-256.
- Пока не выполнены Gradle и физические инструментальные испытания, статус **не подтверждён**.
